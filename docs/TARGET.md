### 核心设计原则

1.  **即时性 (Immediacy)**：用户的操作应立即产生结果。核心交互是“放置文件”，而不是“放置文件，然后点击按钮”。从用户放下文件的那一刻起，系统就接管了工作。
2.  **清晰的单一焦点 (Single, Clear Focus)**：界面上永远只有一个主要任务区域——文件拖拽区。所有其他元素都是对这个核心任务的辅助和状态反馈。
3.  **克制的反馈 (Restrained Feedback)**：UI 的状态变化应当清晰、不突兀。通过 subtle 的动画、图标和文本变化来告知用户当前状态（等待、处理中、成功、失败），避免过度的视觉干扰。

### 核心用户流程与状态定义

我们可以将应用看作一个简单的状态机。

1.  **初始状态 (Ready)**
    *   界面中心是一个明确的拖拽区域，有简单的引导文案，如“将文件或文件夹拖拽至此”。
    *   界面下方有一个输出路径选项：“在原位置旁创建转换后的文件”，此项默认勾选。

2.  **文件悬停状态 (Hovering)**
    *   当用户将文件拖拽到窗口上方时，拖拽区域应有视觉反馈，例如边框高亮或背景色变化，表明这是一个可交互的目标区域。

3.  **文件置入与处理流程 (Processing Flow)**
    *   这是关键。用户在拖拽区域松开鼠标的瞬间，流程立即开始，不存在中间的“确认”或“转换”按钮。
    *   **分支 A：默认输出路径（复选框勾选）**
        *   文件被置入。
        *   UI 立刻进入“处理中”状态（例如，显示一个轻量的加载动画或进度指示）。
        *   前端根据文件名调用相应的后端 bin。
        *   后端处理完成。
    *   **分支 B：自定义输出路径（复选框未勾选）**
        *   文件被置入。
        *   系统**立即**弹出原生文件选择对话框，提示用户“请选择保存位置”。
        *   用户选择路径并确认。
        *   UI 进入“处理中”状态。
        *   前端调用后端 bin，并附带 `-o` 或 `--output` 参数。
        *   后端处理完成。

4.  **完成状态 (Completed)**
    *   “处理中”状态消失。
    *   界面显示结果。
        *   **成功**：显示简洁的成功信息，如“转换完成”，并可能附带一个“在访达/资源管理器中显示”的链接，方便用户快速定位文件。
        *   **失败**：显示明确的错误信息，如“文件格式无法识别”或“转换失败”。如果后端返回了具体的错误日志，可以提供一个“查看详情”的选项，以非侵入式的方式展示。
    *   完成状态应在几秒后或用户下一次拖拽文件时自动重置回**初始状态**。

### 组件与交互细节

*   **拖拽区域**
    *   是界面的视觉主体。
    *   在不同状态下（Ready, Hovering, Processing, Completed）有不同的视觉表现。
    *   在 Ready 状态下，可以显示应用图标和一个简短的动词引导，如“拖入文件”。
    *   在 Processing 状态下，可以显示一个无限循环的加载指示器。
    *   在 Completed 状态下，显示结果图标（对勾/叉）和状态文本。

*   **输出路径选项**
    *   形式为一个复选框（Checkbox）和一个标签文本。
    *   文本：“在原位置旁创建转换后的文件” 或 “保存到同一文件夹”。
    *   默认选中。
    *   用户的选择会持久化（记住用户上一次的设置）。
    *   它的状态（勾选/未勾选）直接决定了**文件置入后**的流程分支，而不是在点击时触发任何即时动作。这避免了误操作带来的干扰。

*   **状态反馈文本**
    *   一个位于拖拽区域下方的次要文本区域。
    *   用于显示当前处理的文件名、识别出的转换器类型、或最终的成功/失败信息。这为用户提供了上下文，但不干扰主要视觉区域。

### 后端调用与文件路由

*   **触发时机**：文件被置入后，并且输出路径确定后（无论是默认还是用户选择）。
*   **路由逻辑**：前端根据拖入的文件/文件夹名称进行判断。这个规则可以保持简单。
    *   文件名含 `cherry` -> 调用 `cherry-studio-backup-json-converter`。
    *   文件名含 `qwen` -> 调用 `qwen-json-converter`。
    *   文件名含 `rikka` -> 调用 `rikkahub-db-converter`（RikkaHub 备份 zip / db）。
    *   其他情况（如文件夹或无明确关键词的文件） -> 调用 `google-ai-studio-json-converter`。
*   **参数传递**：
    *   输入路径：拖拽的文件/文件夹的绝对路径。
    *   输出路径：如果用户自定义了路径，则通过 `-o` 参数传递；否则，不传递该参数，依赖 bin 的默认行为。

### 视觉与动画指导

*   **过渡动画**：状态切换应有平滑的淡入淡出（fade）或位置微调（translate）过渡，时长建议在 150ms-250ms 之间，以保证响应的即时感。
*   **颜色**：使用中性色作为基础，用单一的主题色来表示可交互元素和成功状态，用警示色（如橙色或红色）来表示错误状态。
*   **字体与间距**：保持一致的字体层级和足够的留白，创造一个干净、无压力的视觉环境。

## 技术约束

1.  **技术栈**：Tauri。
2.  **后端集成**：仅通过 tauri::api::process::Command 调用 `bin/` 目录下的可执行文件，不修改其源码。
3.  **平台**：保持跨平台兼容性 (macOS, Windows, Linux)。
