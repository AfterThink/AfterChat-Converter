# AfterChat-Format 规范 (AfterChat-Format Specification RFC)

> **版本**：1.0.0-draft
> **状态**：AfterChat 生态统一标准 (Active)  
> **定位**：大语言模型（LLM）对话导出、交换与本地归档规范。
>
> 本规范完整定义了 AfterChat 生态中 LLM 对话的 Markdown 表示结构与 ZIP 打包归档格式，是所有导出端、转换端与消费端遵循的单一事实来源（Single Source of Truth）。

---

|---|---|---|---|

| **转换端 (Offline Migration)** | [AfterChat-Converter](https://github.com/AfterThink/AfterChat-Converter) | Rust (`crates/afterchat-chatformat`) | 离线历史备份解析与批量转换，提供公共的规范渲染与打包库 |

## 0. 任务定义

| | 输入 | 输出 |
|---|---|---|
| 单个会话 | 单个会话数据源 | 单个 `.md` 文件 |
| 批量导出（含多个会话） | 备份文件 / 数据库 / 压缩包 | 单个 `.zip` 文件（内含多个 `.md`） |

各平台的差异仅存在于**输入数据的解析逻辑**（提取会话、消息体、角色及时间戳）。
**输出的 Markdown 格式与打包规范对所有平台及所有实现端完全统一**，转换器与导出脚本必须严格遵循第 1 至第 7 节的规范。

> **输入读取建议**：部分平台的导出产物为内含数据文件的 ZIP 压缩包（路径层级不固定且可能包含 BOM）。
> 建议直接在内存或流式读取压缩包内部条目，避免解压到磁盘，以提升处理性能并规避路径遍历等安全风险。若包含 UTF-8 BOM 须主动剔除。

---

## 1. 物理约束

- **文件扩展名**：`.md`
- **字符编码**：UTF-8（允许存在 UTF-8 BOM，解析端应兼容并主动剥离）
- **换行符**：支持 `LF` 与 `CRLF`（跨平台兼容）
- **缩进规范**：不强制指定缩进空格数

---

## 2. 文件结构骨架

```markdown
## Metadata

- **Model:** `模型名`
- **Time:** 2026-09-17 21:19:12 +08:00
- **URL:** https://平台地址/对话id

## Conversation

### ⚙️ System

（系统提示词，可选；若缺失则整段省略）

### 🧑‍💻 User

（用户输入内容）

### 🤖 Assistant

#### 🤔 Thought Process

（思维链内容，可选）

#### 💡 Response

（助手正式回复内容）

### References

- [1] [标题一](https://example.com/1)
- [2] [https://example.com/2](https://example.com/2)
```

---

## 3. Metadata 区

**位置约束**：位于文件顶部，必须出现在 `## Conversation` 分隔行之前。

| 键名 | 语法格式 | 规范说明 |
|---|---|---|
| `Model` | `` - **Model:** `模型名` `` | **必填**。模型标识符，**必须用行内代码反引号包裹**（见下方警告） |
| `Time` | `- **Time:** 2026-09-17 21:19:12 +08:00` | **可选**。会话发生本地时间，采用 `YYYY-MM-DD HH:mm:ss ±HH:MM` 格式，**严禁添加反引号** |
| `URL` | `- **URL:** https://…` | **可选**。原始会话链接，若缺失则省略该行 |

> ⚠️ **`Model` 字段格式约束**：解析端依赖正则表达式 `/- \*\*Model:\*\* `(.*?)`/` 进行模式提取。任何多余空格或反引号缺失均会导致模型元数据提取失败。

- 除 `Model` 必填外，其余字段均为可选。**允许追加平台特有的扩展键**（例如 `- **Topic ID:** `x``、`- **Assistant:** `y``），建议置于标准键之后；解析端会忽略未知键。
- Metadata 区域内可添加 `### 小节`，但**严禁包含消息正文**；正文必须置于 `## Conversation` 之后。
- 时间戳须取会话自身的实际发生时间，不得使用转换执行时的系统时间。

## 4. Conversation 正文区

### 4.1 正文分隔行（Conversation Delimiter）

正文区起始处必须有且仅有一行二级标题 `## Conversation`。

### 4.2 角色标识头（Role Headers）

| 角色 | 标题行 |
|---|---|
| 用户 | `### 🧑‍💻 User` |
| 助手 | `### 🤖 Assistant` |
| 系统提示 | `### ⚙️ System` |
| 无法识别的角色 | 统一回退至 `### 🤖 Assistant` |

- **消息作用域**：单条消息内容界定于**当前角色头至下一角色头（或文末 References 附录）之间**的全部文本；
- **消息时序**：各角色消息排列必须与原始对话的实际发生时间严格保持一致；
- **空消息跳过**：无有效内容的空消息须**直接跳过**，避免生成孤立的角色标题；
- **系统提示词定位**：系统提示词（System Prompt）作为**对话的首条消息**输出，位于首个用户或助手消息之前。

> ⚠️ 解析端通过正则表达式 `^###\s+.*\b(User|Assistant)\b.*$` 识别角色边界。
> 因此正文内部严禁出现未经转换的 `###` 行（参见第 5 节）；否则包含 `User` 或 `Assistant` 单词的正文标题会被误判为新的消息分块，导致消息截断。

### 4.3 助手思维链与回复内容分段

助手消息依据内容类型分为思维链（Thought Process）与正式回复（Response）两部分。**每类内容在同一助手消息中仅允许出现一个对应的四级标题**（同一消息内若存在多个思维片段须予以合并）：

```markdown
### 🤖 Assistant

#### 🤔 Thought Process

（思维链内容）

#### 💡 Response

（正式回复内容）
```

- **标题精确匹配**：标题行文字必须严格保持字面一致（包括 Emoji 图标与空格），严禁擅自增删空格或替换图标。
- **换行与空行约束**：四级标题行后**必须空一行（即紧跟换行后空一行）**再书写正文内容，严禁正文紧贴在标题行末（例如：❌ `#### 💡 Response正文直接贴上来`；✅ `#### 💡 Response` + 空行 + 正文）。
- **缺省与存在性规则**：
  - 当助手消息无思维链时，严禁输出 `#### 🤔 Thought Process` 标题行，正文直接跟在角色头后即可；
  - 当助手消息仅包含思维链而无回复时，仅输出思维链段落，严禁输出空的 `#### 💡 Response` 标题行。
- **多片段拼接**：思维链或回复内容内部若存在多个离散文本块，统一使用双换行符 `\n\n` 进行连接。

### 4.4 全局引用与信源区（References，可选）

若对话中包含联网搜索信源或模型输出的引用来源，在正文最后一条消息结束之后，统一追加全局引用附录：

```markdown
### References

- [1] [标题文本](https://example.com/1)
- [2] [https://example.com/2](https://example.com/2)
```

#### 4.4.1 结构约束与触发条件

- **位置**：必须位于整场对话**最后一条消息正文结束之后**。
- **排版过渡**：由空行自然过渡至 `### References`，**不使用 `---` 分割线**（保持与 `## Metadata` 到 `## Conversation` 及各角色消息间一致的无横线极简排版）。
- **标题行**：固定为三级标题 `### References`（精确字符串，不要加 emoji、不要改大小写）。
- **存在性**：整场对话若无任何有效引用信源，**严禁输出空的 `### References`**。

#### 4.4.2 正文行内引用角标（In-text Citation Markers）

- **标号格式**：一律采用 `[N]`，其中 `N` 为正整数（`1`, `2`, `3`…）。
- **多引用连续连排**：当同一处引用多个信源时，采用紧凑连排格式 `[1][2]`（不加空格，不加逗号，解析端最稳定）。
- **空白排版规范**：
  - **中文标点**：中文全角标点（`。` `，` `！` `？` `；` `：` 等）自带字形空距，标点后直接紧接 `[N]`，**严禁在标点与角标之间插入额外空格**（例如：`……根据最新报告。[1]`）。
  - **英文标点**：英文半角标点（`.` `,` 等）后紧跟角标 `.[1]`，**不插入空格**，以避免 Markdown 换行折行时产生孤立行首角标。
  - **行内单词间**：当引用位于句子中间非标点处时，必须保留西文单词正常的词间空格（例如：`according to [1] and [2]`）。严禁使用激进的全局正则无差别抹杀 `[N]` 之前的所有空格。

#### 4.4.3 列表项格式标准化（Markdown 链接化）

信源列表项统一采用无序列表 + 标准 Markdown 超链接格式：

- **标准带标题项**：`- [N] [标题文本](URL)`
- **无标题项（标题缺失或与 URL 一致时）**：`- [N] [URL](URL)`
- **规范要求**：URL 必须用标准 Markdown 行内链接 `[...](...)` 包裹，禁止输出裸 URL 或未链接的纯文本，保证在所有 Markdown 阅读器中均可直接点击跳转。

#### 4.4.4 URL 规范化与去重（Canonical Deduplication）

- **URL 规范化**：收集信源时须做规范化清洗：
  1. 移除首尾空白；
  2. 移除路径末尾非根路径的冗余斜杠（如 `https://example.com/page/` → `https://example.com/page`）；
  3. 移除常见的追踪与打点参数（如 `utm_*`、`spm` 等）；
  4. 移除与页面正文定位无关的临时 Hash。
- **全局去重与复用**：整场对话中，凡规范化后相同的 URL 必须复用首次分配的全局编号 `[N]`，正文各处多次引用该链接时均标注相同的 `[N]`。References 列表中每一条信源 URL 必须全局唯一，严禁出现多个条目指向同一个 URL 的冗余现象。
- **全局单调递增**：在多轮对话中，引用的全局编号必须从 `1` 开始单调递增连续排列（1..K），文末列表按序号正序排列，严禁多轮各自重新从 `[1]` 开始计数的重号冲突。

## 5. 消息体转换规则

### 5.1 标题语法转换（`#` 转换为加粗）

正文中的 Markdown 标题行（`#`、`##`、`###` 等），**必须统一转换为行内加粗强调**：

```
# 一级标题        →  **一级标题**
### 1. 基本构成   →  **1. 基本构成**
```

**转换规则与处理流程**（逐行处理，行首必须是列 0 的 `#`）：

> **作用域约束**：本规则**仅作用于对话消息体正文**。规范自身定义的结构标题（包括 `## Metadata`、`## Conversation`、角色标识头 `### 🧑‍💻 User` 等、思维链/回复标识 `#### 🤔 Thought Process` / `#### 💡 Response`、以及 `### References`）属于转换器产出的结构标识，严禁应用此加粗转换规则。

1. 匹配行首标题语法：`^#{1,6}\s+(.+)$`（`#` 之后必须包含至少一个空白字符，且紧跟至少一个非空字符）；
2. 提取标题主体文本：`inner = 匹配文本.trim()`；若 `inner` 为空，则整行原样保留；
3. 输出加粗结果：`**` + `inner` + `**`。

**不匹配（保持原样）的场景示例**：`####### 七个井号`（连续井号超过 6 个）、`#紧贴文字`（`#` 之后无空白字符）、`# `（无有效正文内容）。

### 5.2 标题内层加粗吸收

若原始标题文本中已包含 `**` 加粗标记，直接在外层包裹加粗会导致 CommonMark 定界符错配，产生局部强调异常或**残留可见星号**：

```
## 方案一：**“水珠胶囊”——像吃水果一样喝水**
   ❌  **方案一：**“水珠胶囊”——像吃水果一样喝水****     ← 产生可见多余星号
   ✅  **方案一：“水珠胶囊”——像吃水果一样喝水**          ← 规范整条加粗
```

**转换策略**：在外层包裹 `**` 之前，移除标题内容中**所有处于行内代码段外部**的 `**` 标记。因整行标题已置于加粗中，内层加粗属于冗余样式。

**注意：必须保留行内代码内部的 `**`**（此情况为内容本身而非强调标记，如 glob 语法）：

```
# 匹配 `**/*.js` 的路径   →  **匹配 `**/*.js` 的路径**     ✅
                              **匹配 `/*.js` 的路径**      ❌ 破坏了 glob
```

行内代码的界定用 CommonMark 规则：**N 个反引号开始，同样 N 个反引号结束**。

### 5.3 须保持原样的 `#` 场景

| 场景 | 示例 | 处理方式 |
|---|---|---|
| **围栏代码块内部** | `` ```python `` … `# 注释` … `` ``` `` | 保持原样 |
| **缩进代码块** | `    # 缩进 4 空格` | 保持原样（非行首第 0 列的 `#`） |
| **行内代码内部** | `` `# not a heading` `` | 保持原样 |

代码围栏支持使用 `` ``` `` 或 `~~~`，须**成对匹配**（`` ``` `` 仅能由 `` ``` `` 闭合，无法由 `~~~` 闭合）。
围栏标记允许包含前导空格；语言标注（如 `` ```python ``）不影响匹配逻辑。

> **实现原则**：严禁误改代码块内的字符。将代码中的 `#` 误转为加粗属于破坏性变更，因此对代码围栏与缩进块的识别策略应采取保守判定。

### 5.4 内容完整性约束

- 保持 Markdown 原始排版：列表、引用、表格、链接、常规加粗/斜体及行内代码等均保持原样；
- 禁止对正文各行进行无意义的重排或全局 `trim`；
- 禁止引入额外的字符转义或 HTML 实体转义。

**参考实现（伪代码）**：

```
function strip_hashes(text):
    fence = null                      # null / "```" / "~~~"
    for line in text.split("\n"):
        marker = "```" if line.trim_start().starts_with("```")
                 else "~~~" if line.trim_start().starts_with("~~~")
                 else null
        if fence != null:             # 围栏内：原样输出
            output(line)
            if marker == fence: fence = null
        elif marker != null:          # 围栏开始
            fence = marker; output(line)
        else:
            output(strip_one_line(line))   # 单行转换处理

function strip_one_line(line):
    n = count of leading '#' in line      # 必须从列 0 开始计数
    if n == 0 or n > 6: return line
    rest = line[n:]
    if rest is empty or rest[0] is not whitespace: return line
    inner = rest.trim()
    if inner is empty: return line
    return "**" + remove_bold_outside_code(inner).trim() + "**"

function remove_bold_outside_code(text):
    out = ""; open_ticks = 0; i = 0
    while i < len(text):
        if text[i] == '`':
            run = count of consecutive '`' at i
            if open_ticks == 0: open_ticks = run
            elif open_ticks == run: open_ticks = 0
            out += text[i : i+run]; i += run
        elif open_ticks == 0 and text[i:i+2] == "**":
            i += 2                      # 吸收内层多余强调标记
        else:
            out += text[i]; i += 1
    return out
```

## 6. 归档与打包规范

### 6.1 单会话导出（Single Conversation）

输出形态为单个独立 `.md` 文件，文件名采用清洗后的会话标题：`{标题}.md`（清洗规则参见第 7 节）。

### 6.2 批量归档压缩包（Batch ZIP Archive）

批量导出多场会话时，统一打包为单个标准 ZIP 压缩文件。

#### 6.2.1 归档文件名格式

```
chat-export-{platform}-all-{毫秒时间戳}.zip
```

- `{platform}`：数据源平台短名，全小写字母（例如 `qwen`、`cherry`、`m365` 等）；
- `{毫秒时间戳}`：归档生成时刻的 Unix 毫秒时间戳（13 位整数）。

#### 6.2.2 归档内部条目命名与结构

压缩包内部条目支持以下两种路径组织方式：

```
{YYYYMMDD-HHmmss}-{标题}.md          ← 扁平单层结构（推荐）
platform/{YYYYMMDD-HHmmss}-{标题}.md  ← 平台子目录分组结构
```

- **时间戳前缀**：时间戳须取**会话自身的发生时间**（而非导出归档时间），格式为 `YYYYMMDD-HHmmss`；
- **缺省序号回退**：若会话缺失有效时间戳，采用 3 位零填充递增序号作为前缀兜底（例如 `001-{标题}.md`）；
- **重名冲突处理**：当压缩包内存在同名条目时，在文件名主体末尾、扩展名之前追加序号后缀（例如 `-2`、`-3`，形如 `{YYYYMMDD-HHmmss}-{标题}-2.md`），严禁静默覆盖；
- **条目物理时序**：压缩包内部条目建议按会话发生时间**由远及近（时间正序）**依次排列；
- **压缩编码**：推荐采用标准 Deflate 算法压缩存储；
- **条目修改时间（Entry Timestamp）**：
  - 各会话条目的文件修改时间（mtime）应设置为该**会话的发生时间**；
  - *精度说明*：ZIP 格式规范采用 MS-DOS 时间戳，时间精度为 2 秒（奇数秒向下取偶），允许存在不超过 1 秒的格式舍入误差。

### 6.3 失败诊断报告（Export Failure Report）

若在批量导出或转换过程中存在因数据损坏等原因**完全无法导出**的会话，须在 ZIP 根目录额外生成一份 `export-failures.md`：

- **内容要求**：详尽记录未成功导出的会话标题、唯一标识（ID）及具体失败原因；
- **文件修改时间**：作为本次导出的诊断日志，该条目的修改时间直接设为**当前归档生成时间**；
- **存在性约束**：若全部会话均成功导出（无失败用例），**严禁生成此文件**。

## 7. 标题到文件名转换与净化

在将会话标题转换为本地文件名或 ZIP 条目名时，须执行以下标准化清洗规则：

- **非法字符过滤**：剔除跨平台（特别是 Windows 文件系统）保留的非法字符：`\`、`/`、`*`、`?`、`:`、`"`、`<`、`>`、`|`，以及空白控制符 `\r`、`\n`、`\t`；
- **首尾空白裁剪与缺省回退**：执行 `trim()` 裁剪首尾空白；若净化后文件名为空，必须使用标准占位名称兜底（例如 `Untitled` 或 `Untitled_Conversation`）；
- **长度截断建议**：为规避文件系统路径长度溢出（如 Windows `MAX_PATH`），建议对条目文件名主体长度进行截断（通常限制在 60 至 80 个字符以内）；
- **禁止转义污染**：净化过程中**严禁执行 HTML 实体转义或 Markdown 转义**（例如不得将 `&` 转为 `&amp;` 或将 `_` 转为 `\_`），确保文件系统纯净可读。

### 8.3 整条加粗断言

针对 8.1 中所有已执行加粗转换的输出，须满足如下不变式断言：

> 结果以 `**` 开头、以 `**` 结尾，且**中间不再出现 `**`**（行内代码段之内的 `**` 除外）。

该断言无需依赖全功能 Markdown 渲染管线即可高效校验，是验证整条标题被完整强调且无残留可见星号的充分必要条件。

### 8.4 渲染语义验证（端到端校验）

若测试环境集成有标准 CommonMark 渲染管线（例如 JavaScript `markdown-it` 或 Rust/Python 对应库），建议补充以下 HTML 语义断言：

1. 最外层 `<strong>` 标签完整包裹全部可见正文文本；
2. 剔除 `<code>…</code>` 行内代码后，可见文本中不存在未配对的可见星号 `*`。

### 8.5 结构完整性验证

对每份产出的 `.md` 文件执行以下结构断言：

- 文件以二级标题 `## Metadata` 起始；
- 包含有效模型声明 ``- **Model:** `…` ``（必须包含行内代码反引号）；
- `Time` 严格匹配时间格式 `^\d{4}-\d{2}-\d{2} \d{2}:\d{2}:\d{2} [+-]\d{2}:\d{2}$`；
- 正文区以二级标题 `## Conversation` 开头，且全文有且仅有一处；
- `#### 💡 Response` 与 `#### 🤔 Thought Process` 独占一行，其后紧随空行后再输出正文；
- 若存在 `### References`：由空行自然承接（不包含 `---` 分割线），每一项均遵循 `- [N] [...]` 格式，序号自 `1` 开始单调递增且无重复；
- 消息体正文（代码围栏之外且行首位于列 0）不存在未转换的 `^#{1,6}\s+\S` 标题行（角色头、`#### 🤔`/`#### 💡` 及 `### References` 结构标题除外）。

## 9. 注意事项与边界条件

| 场景 | 影响 |
|---|---|
| `#### 💡 Response` 标记后未换行 | 解析端将整行视为无内容的标题，导致内容索引与定位失败 |
| 正文 `#` 标题未转换为加粗 | 违反格式规范；若标题包含 `User`/`Assistant` 等关键字会导致消息被截断拆分 |
| 标题内层 `**` 未被吸收 | 渲染时出现多余星号且样式解析不全 |
| 误删行内代码中的 `**` | 破坏 glob 路径或代码原有语义 |
| 误转换代码围栏内的 `#` | 破坏 Python/Shell 等脚本注释语法 |
| `Model` 字段遗漏反引号 | 解析端无法准确通过正则提取模型名称 |
| 采用当前系统时间而非会话时间 | 时间线排序错乱，基于时间的归档功能失效 |
| 空消息输出孤立角色头 | 产生无有效内容的空白消息气泡 |
| 未剔除 UTF-8 BOM | 导致部分 JSON 反序列化库解析失败 |
| ZIP 内部条目重名未处理 | 导致同名文件被覆盖丢失 |
| References 包含重复 URL | 产生冗余噪音，降低归档品质；应规范化去重并复用 `[N]` 标号 |
| References 采用裸 URL 或纯文本 | 降低在各 Markdown 查看器中的可交互性；应统一采用 `- [N] [标题](URL)` |
| 激进抹除角标前的所有空格 | 误将英文单词与引用黏连（如 `word[1]`）；应仅约束中英文标点贴合，保留单词间合理空格 |
| 多轮对话引用各自从 `[1]` 重计 | 文末列表出现重复编号与角标冲突；必须做全局递增重映射 |
